# Design

## 为什么不让 DOM 直接拥有快捷键

原生菜单项必须继续显示 `⌘S` 等键位（可发现性，且 `native-menu-bar` 规范要求加速键与菜单项一致）。若把执行权整体搬回 DOM，菜单栏的键位提示就成了谎言；若把加速键从菜单上摘掉，`⌘S` 的提示会消失。因此保留「菜单优先」，DOM 只做兜底。

## 判定「菜单是否接管」的依据

AppKit 在把 `keyDown` 交给响应链（含 webview）之前先做菜单键位匹配。菜单匹配成功，webview 收不到该 `keydown`。所以 `initKeyboard` 里看到的事件本身就是「菜单没有接管」的证据——不需要额外探测，也不需要读菜单启停状态。

## 去重为什么按「来源」而不是「时间」

跨入口去重的目标是「一次物理按键被两个入口各上报一次」。若只按时间窗口去重，用户刻意的连按会被吞。因此记录 `origin`，只有跨来源且落在窗口内才判定为同一次按键；同来源重复一律执行。

被判定为重复的那次 MUST NOT 刷新时间窗：否则一串重复会不断把窗口前移，把后续真实按键也吞掉（复核复现过该级联）。

## 120ms 的取值与已知失效模式

窗口只需覆盖一次 `menu:action` IPC 往返（毫秒级）。取 120ms 留足余量，同时远小于人类的刻意连按间隔。

已知失效模式：若主线程被长任务阻塞，同一次按键的两个上报可能相隔超过窗口，命令会执行两次；对 `bold`/`toggle-mode` 这类幂反命令表现为「按了没反应」。窗口不宜再放大——放大会把「两次不同按键」也并入同一次。Rust 侧在 `menu:action` 里带激活序号可做确定性关联，属后续优化。

## 日志提级

`backend.menu: Native menu action` 由 `debug` 提到 `info`。`src-tauri/src/logger.rs` 的 release 级别是 `INFO`，原级别导致发布构建里无法区分「菜单没收到动作」与「收到但派发失败」——本次排障只能靠 GUI 实测，不该每次如此。一次用户激活一行，量级可接受。

## 依赖注入而非模块级全局

`keyboard.ts` 处于 `utils` 层，不得 import `ui`。因此用 `initKeyboard({ onShortcut })` 参数注入，由装配根 `src/main.ts` 接线，避免反向依赖与循环依赖（`check-layering` 的 SCC 检查通过）。

## 提示为什么在渲染时格式化，而不是写两套文案

#406 的成因是提示与加速键各写一遍：菜单声明 `Mod+S`，提示手写 `Ctrl+S`。两处独立维护，改一处不会带动另一处，平台差异就被固化成了错误文案。

另一条路是在 HTML 里各写一份 `⌘S` 和 `Ctrl+S`、用 CSS/JS 择一显示。这样文案仍是两份手写，仍然会漂移，还会污染可访问名（隐藏的那份仍在 DOM 里）。

因此提示与菜单共享同一种平台无关声明（`Mod+S`），在渲染时投影成当前平台的写法。声明只有一处，漂移不可能发生。

## `Mod` 与 `Ctrl` 必须分开

`Mod` 表示平台主修饰键（macOS `⌘`），`Ctrl` 表示**真正的** Control（macOS `⌃`）。两者混用会把 `Ctrl+Tab`（macOS 上确实是 `⌃Tab`）错误渲染成 `⌘Tab`——那是切换应用，不是切换标签。`src/utils/shortcut.ts` 对这两个 token 分别映射。

## 可测性：平台判定放在 infra 层、每次调用时读取

`formatShortcut` 是纯函数，平台作为入参；`shortcutPlatform()` 只在 `src/infra/platform.ts` 里读 `navigator.platform`（带 UA 兜底），且每次调用时读、不缓存到模块级常量——测试里改写 `navigator` 即可切换平台，无需切换构建目标或注入全局配置。

## 静态 HTML 的接入方式

`index.html` 在应用启动前就已存在，不可能在那时知道平台。因此工具栏提示声明为 `data-tooltip="…" data-shortcut="Mod+S"`，由 `applyShortcutHints()` 在启动时把渲染结果补进 `data-tooltip` 与 `title`。

`applyShortcutHints` 必须幂等：它可能在重渲染或语言切换后再次运行。实现上先剥掉上一次追加的键位后缀再追加（或用"基串 + 当前键位"拼装），否则会出现「保存 (⌘S) (⌘S)」。
